# Hermes 升级韧性设计

> 维护者：Jentle ｜ 版本：v1.0 ｜ 最后更新：2026-08-23
> 本文回答一个问题：**Hermes 升级后插件会不会失效？能不能做到无残留、无冲突？**

---

## 一、先给结论

| 方案 | Hermes 升级后 | 残留 | 冲突风险 | 失效可见性 |
|---|---|---|---|---|
| AST 源码注入（HLS / HFC 的做法） | **必然失效** | 有（.bak、marker 块） | 高（多插件抢同一段源码） | **静默失效** |
| **运行时织入（本插件采用）** | **不受影响** | **零** | **无** | 启动即报错 |

**本插件采用运行时织入，把源码注入降级为"降级预案"而非主方案。**

代价说明：运行时织入不是绝对免疫。它依赖 Hermes 保持「回调以实例属性形式装配到 `AIAgent`」这一装配方式。若 Hermes 改掉这个机制，织入同样会失效——**但会在 gateway 启动时立刻报错，不会像源码注入那样静默失效**。这个差别，在生产环境里比"能不能免疫"更重要。

---

## 二、为什么 AST 注入必然失效

### 2.1 升级动作直接覆盖被注入的文件

Hermes 的升级路径是 git reset + 重装依赖。这一点在 Hermes 自身源码的注释里有直接证据：

```python
# ~/.hermes/hermes-agent/gateway/run.py:20-25
except ModuleNotFoundError:
    # Graceful fallback when hermes_bootstrap isn't registered in the venv
    # yet — happens during partial ``hermes update`` where git-reset landed
    # new code but ``uv pip install -e .`` didn't finish.
```

`git-reset landed new code` —— 升级会用 git reset 覆盖工作区文件。任何写进 `gateway/run.py` 的 marker 块，在这一步会被**整体抹掉**。

### 2.2 失效方式是"静默"的，这才是真正的问题

marker 块被抹掉后：

- 插件包仍然装在 venv 里，`import hermes_lark_streaming` 正常
- 但再没有任何代码调用它的 hook
- Gateway 正常启动、正常回消息，**只是卡片不再出现**
- 日志里没有任何错误

用户看到的是"插件突然不工作了"，排查要从头开始。HFC 为此专门做了残留状态检测和 `--accept-hermes-upgrade` 重装流程，HLS 则要求用户手动 `uninstall` → `verify` → `install` → 重启。两者都无法避免"升级后有一段时间处于静默失效状态"。

### 2.3 残留与冲突

- **残留**：`.hermes_lark.bak` 留在 Hermes 目录里，且内容是**升级前**的旧版本。若此时误执行 `restore`，会用旧代码覆盖新 Hermes，造成更严重的损坏
- **冲突**：多个 patch 类插件注入同一个函数时，marker 块互相嵌套，卸载顺序错误就会留下孤儿代码。当前这台机器上 `gateway/run.py` 已被 `HERMES_LARK_*` marker 注入（见 run.py:5989、6055、6178），本插件若也走注入路线，就要处理这类共存问题

## 三、运行时织入方案

### 3.1 核心原理

Hermes 装配 Agent 回调的方式是**对实例做普通属性赋值**：

```python
# gateway/run.py:5953-6004
agent.stream_delta_callback = _stream_delta_cb
agent.interim_assistant_callback = _interim_assistant_cb
agent.status_callback = ctx._status_callback_sync
agent.notice_callback = _notice_callback_sync
agent.reasoning_callback = _reasoning_cb
agent.background_review_callback = _bg_review_send
agent.clarify_callback = _clarify_callback_sync
agent.tool_progress_callback = ctx.progress_callback
```

Python 的属性查找规则给了我们一个稳定的拦截点：**定义了 `__set__` 的类属性（数据描述符）优先级高于实例 `__dict__`**。也就是说，只要在 `AIAgent` 类上装一个描述符，上面每一行赋值都会先经过我们的代码：

```text
agent.stream_delta_callback = 原回调
                │
                ▼
   AIAgent 类上的描述符 __set__ 被触发
                │
                ├─ 把原回调包装成 「先喂卡片，再决定是否透传」
                └─ 包装结果存进 instance.__dict__
                │
                ▼
   Agent 运行时读到的是包装后的回调
```

**全程不修改任何 Hermes 源码文件。**

### 3.2 可行性验证（已完成）

| 前提 | 结论 | 证据 |
|---|---|---|
| `AIAgent` 没有 `__slots__`，实例有 `__dict__` | **成立** | `run_agent.py:3282` 使用 `vars(self).get(...)`；有 `__slots__` 的类调用 `vars()` 会抛 `TypeError` |
| Gateway 会往 agent 实例上挂任意属性 | **成立** | `run.py:6013` 挂 `_gateway_turn_context_notes`；`run.py:6223` 挂 `_gateway_turn_process_task_id`。这类动态属性在 `__slots__` 类上不可能成立 |
| 回调以实例属性赋值装配 | **成立** | `run.py:5953-6004` 连续 8 处赋值 |
| `AIAgent` 可被 import 并 monkey-patch | **成立** | `run_agent.py:17` 文档示例 `from run_agent import AIAgent`；`run_agent.py:55` 注释提到测试用 `patch("run_agent.OpenAI", ...)` 模式 |
| 数据描述符优先于实例 `__dict__` | **成立** | Python 语言规范保证，非实现细节 |

以上五条置信度均为【确定】，每条都有源码行号或语言规范支撑。

### 3.3 织入入口：官方插件 entry point

织入代码本身也需要一个执行时机，且这个时机不能依赖修改源码。用 Hermes 的官方插件机制：

```toml
[project.entry-points."hermes_agent.plugins"]
hermes-lark-streaming = "hermes_lark_streaming.bridge.plugin"
```

这个 entry point 由 **pip 安装时写入 venv 的元数据**，位置在 `site-packages`，**不在 Hermes 的 git 工作区内**。因此 `git reset` 不会碰它，Hermes 升级后依然存在。

Hermes 启动时加载插件，调用我们的 `register(ctx)`，我们在其中完成描述符安装。

### 3.4 织入范围

只织入必要的回调，未列出的一律不碰：

| 回调 | 织入目的 |
|---|---|
| `stream_delta_callback` | 答案流式 → 卡片打字机 |
| `interim_assistant_callback` | 思考流式 → 卡片折叠面板 |
| `reasoning_callback` | 原生推理 → 卡片折叠面板 |
| `tool_progress_callback` | 工具调用 → 卡片时间线 |
| `status_callback` | 状态提示 → **收进卡片**（治理游离消息） |
| `notice_callback` | 额度通知 → **收进卡片** |
| `background_review_callback` | 自我改进 → **收进卡片** |
| `clarify_callback` | 澄清 → 卡片状态块 |

`send_exec_approval` / `send_clarify` 这类适配器方法不在 `AIAgent` 上，走另一条路径（实例方法织入，见架构设计决策 2），原理相同：不改源码，只改运行时对象。

除回调之外还织入三处**类方法**，同样不碰源码：

| 目标 | 位置 | 织入目的 |
|---|---|---|
| `AIAgent.run_conversation` 等 | `run_agent.py` | 精确终态收卡（含 model / token / 耗时） |
| `AIAgent.interrupt` | `run_agent.py:3268` | 中断即时定格，并按 `hard_cancel` 区分 /stop 与被新消息接续 |
| `SubagentLifecycleService.launch` / `_run` | `agent/subagent_lifecycle.py` | 委派子任务的启动与终态收进卡片 |

`interrupt` 这一处值得单独说明：HLS 为达到同样的精度注入了 3 个 AST 锚点（ABORT / STOP / INTERRUPT），都在 `gateway/run.py` 的中断判断分支上。而 `interrupt()` 是 Hermes 表达中断的**唯一入口方法**，织它一处即覆盖三种语义，且 gateway 怎么重构都不影响——**注入点的数量差异本身就是耦合深度的度量**。

## 四、四层防御

单靠织入还不够，需要配套的检测与降级。

### 第一层 · 免疫：运行时织入

不写 Hermes 文件，升级不影响。

### 第二层 · 自检：启动即验证

`register(ctx)` 执行时做一次完整自检，任一项不通过就**明确报错并完全退出织入**：

1. `AIAgent` 能否 import
2. 实例是否有 `__dict__`（防 Hermes 改用 `__slots__`）
3. 目标回调属性名是否仍然存在于装配路径中
4. 描述符安装后能否通过一次读写自测（装一个探针对象，赋值再读回，验证包装生效）

自检结果写入日志与 `status` 命令输出，用户执行 `status` 即可看到：

```text
织入状态: ok (8/8 回调已织入)
Hermes 版本: <version>
自检: 通过
```

或在 Hermes 改了机制时：

```text
织入状态: FAILED — AIAgent 使用了 __slots__，无法安装描述符
影响: 流式卡片不可用，已完全退出，Hermes 行为不受影响
建议: 升级本插件版本，或执行 `... install --legacy-patch` 使用源码注入降级方案
```

**这是与源码注入的本质差别：失效变成显式的、启动时可见的。**

### 第三层 · 降级：失败即完全退出

织入的任何一步失败，插件立即停止一切干预，Hermes 回到完全原生的行为。**绝不留下半织入状态**——半织入比不织入危险得多（部分消息进卡片、部分消息游离，用户无法理解）。

实现上用「全有或全无」的两阶段安装：先在探针对象上验证全部描述符可用，全部通过才装到真实类上；中途失败则回滚已装的部分。

### 第四层 · 经验：让失效诊断从笼统变精确

前三层解决「失效时不要拖垮 Hermes」，但没解决「失效后怎么快速定位」。自愈层补上这一环：把每次成功织入的能力集合落盘到 `~/.hermes/hermes_lark_streaming/state.json`，作为下次升级后的对照基线。该目录在 Hermes 主目录下、不在 git 工作区内，因此 `git reset` 碰不到它。

两个信号来源：

- **织入集合** —— `WEAVER.install()` 实际成功织入的回调名列表
- **装配观测** —— 描述符 `__set__` 被触发，说明 Hermes 真的在给这个回调赋值。这是**唯一可靠的存在性信号**：回调是实例属性，静态检查看不到它是否仍在装配路径上（`preflight` 只能检查属性有没有被其他数据描述符占用，检查不出「Hermes 已经不再赋这个值了」）

于是升级后织入失败时，报告不再是一句 FAILED：

```text
织入状态: FAILED — 属性 reasoning_callback 已被 property 占用，不能织入
历史对照: 上次成功织入 8 个回调（Hermes 0.20.5）· 本次缺失 reasoning_callback
```

**装配观测刻意不自动判定「失效」**：部分回调是条件性装配的（`reasoning_callback` 只在开启推理展示时才赋值），本进程没观测到完全可能只是这一轮没触发条件。因此只呈现差异供人判断——这类场景下自动结论必然误报，而误报比不报更糟。

**指纹变化即作废经验**。指纹由实际织入的回调集合计算，刻意不用版本号：`hermes_cli.__version__` 变化远慢于实际代码（同一个 0.20.5 对应几十个 commit），而回调集合本身就是「这套环境长什么样」的直接度量。Hermes 升级导致织入面变化时，上一版学到的降级结论立即失效重学——否则会在本可工作的新环境里白白关闭能力。

## 五、无残留 / 无冲突的保证

### 5.1 无残留

| 检查项 | 运行时织入 | 源码注入 |
|---|---|---|
| 是否写 Hermes 源码文件 | 否 | 是 |
| 是否留备份文件 | 否 | 是（`.bak`） |
| 卸载方式 | `pip uninstall` | 需先 `uninstall` 移除 marker，再 pip 卸载 |
| 卸载后 Hermes 文件状态 | 从未改动，逐字原样 | 依赖 marker 移除是否干净 |
| 忘记卸载直接删包的后果 | 无影响（entry point 随包消失） | **Hermes 源码里留下 import 失败的孤儿代码** |

**一处需要说清的例外**：插件会在 `~/.hermes/hermes_lark_streaming/` 下写两个自己的文件——`state.json`（自愈经验与织入指纹）与 `activity.json`（运行心跳，供 `activity` 命令跨进程判断当前有没有任务在跑）。`pip uninstall` 不会删除它们。

准确的表述是：**不碰 Hermes 的任何文件**，但会留下自己的状态目录。它是插件独占的新建目录，与 Hermes 文件零交集，`rm -rf` 该目录即彻底干净；也可用 `heal reset` 只清经验内容。`selfheal.enabled: false` 会停止写经验文件，心跳仍会写（那是 `activity` 命令的数据来源）。

最后一行是关键差别：源码注入的插件如果被 `pip uninstall` 而没先 `uninstall` marker，Hermes 源码里会残留 `from hermes_lark_streaming.patch import ...`。虽然注入代码都包了 `try/except`，不至于崩，但会在每条消息上抛异常并打日志。运行时织入没有这个失败模式。

### 5.2 无冲突

- **不与其他 patch 插件抢源码**：不写文件，自然不存在 marker 嵌套
- **与已安装的 HLS 共存**：当前机器上 `gateway/run.py` 已有 `HERMES_LARK_*` marker。本插件不写文件，但两者会**同时接管同一批回调**导致重复卡片。因此 `install` 时**强制检测并要求先卸载旧插件**，检测方式是扫描 `gateway/run.py` 中的已知 marker 前缀
- **描述符幂等**：重复 `register` 时检测类上是否已有本插件的描述符（用私有标记属性识别），已安装则跳过，不叠加包装

### 5.3 「完美」的边界

必须说清楚哪些情况仍会失效：

| 情况 | 是否失效 | 表现 |
|---|---|---|
| Hermes 常规升级（改业务逻辑、改文案） | 不失效 | 正常工作 |
| Hermes 重构 `gateway/run.py` 内部实现 | 不失效 | 正常工作（不依赖源码结构） |
| Hermes 新增回调类型 | 不失效 | 新回调不被织入，其余正常 |
| 某类收纳因 Hermes 语义变化而持续失败 | **局部失效** | **只该类降级，其余全部正常**；经验落盘并周期性试探恢复 |
| Hermes 重命名某个回调属性 | 部分失效 | 该回调不再织入；`preflight` 检查不出（回调是实例属性），但运行一个 turn 后 `heal` 会显示它未被观测到 |
| Hermes 给 `AIAgent` 加 `__slots__` | 完全失效 | **启动自检报错并完全退出**，并附上「相比上次成功」的历史对照 |
| Hermes 改为事件总线装配回调 | 完全失效 | **启动自检报错并完全退出** |
| Hermes 移除官方 plugin entry point 机制 | 完全失效 | 插件不被加载，`status` 可查 |

所以准确的表述是：**无残留和无冲突是绝对保证；升级免疫是高概率保证，且失效必定显式可见。**

## 六、降级预案：最小源码注入（**尚未实现**）

设计上保留源码注入作为备用方案，仅在运行时织入被证明不可用时启用。

**当前状态：未实现。** v1.0 只实现了运行时织入这一条路径，`--legacy-patch`
命令行开关尚不存在。若运行时织入在你的 Hermes 版本上不可用，当前的行为是
插件完全退出（Hermes 保持原生，不受影响），而不是自动降级到注入。

若后续确实需要，降级方案的设计约束是：注入点压到 2 个（turn 入口 + 回调注册区
末尾）、事务化 manifest、块外改动检测、幂等安装。但它不会成为默认路径。

## 七、升级后的用户体验

理想情况（运行时织入可用）：

```text
用户执行 hermes update
        ↓
Hermes 源码被 git reset 覆盖
        ↓
插件 entry point 在 site-packages，未受影响
        ↓
gateway 重启，plugin register 被调用
        ↓
自检通过 → 织入成功 → 卡片照常工作
        ↓
用户无感知，无需任何操作
```

Hermes 改了装配机制时：

```text
gateway 重启 → 自检失败 → 日志与 status 明确报错
        ↓
插件完全退出，Hermes 回到原生行为（消息不丢，只是没有卡片）
        ↓
用户执行 status 看到失败原因与建议动作
```

两种情况下，**Hermes 的核心功能都不受影响**——这是稳定性优先原则的最终体现。

### 8.2 实测中发现的额外前提（重要）

**Hermes 的 pip 插件是白名单机制。** `hermes_cli/plugins.py:591-604` 的
`_get_enabled_plugins()` 文档明确写着 *"Plugins are opt-in by default — only
plugins whose name appears in this set are loaded"*；`plugins.py:3940-3945`
进一步显示 `plugins.disabled` 命中即跳过加载（*"Explicit disable always wins"*）。

也就是说，**光 `pip install` 不够**，还必须在 `~/.hermes/config.yaml` 里：

```yaml
plugins:
  enabled: [hermes-lark-streaming]
  disabled: []
```

漏掉这一步的症状是**完全静默不工作**——`register()` 从不被调用，日志里连插件名都不会出现。这是本插件安装路径上最隐蔽的坑，因此 `status` 与 `doctor`
都会主动检查该配置并给出具体修复动作。

本机实测时发现当前 `config.yaml` 恰好是 `enabled: []` 且
`disabled: ['hermes-lark-streaming']`（旧插件靠源码注入工作，不需要 plugin
机制），本插件会被双重拦截。这正是加这项检查的直接动因。

## 一、设计目标与约束

### 1.1 目标优先级（顺序即优先级，冲突时上位覆盖下位）

1. **稳定可靠** — 任何插件侧故障都不得阻断 Hermes 主流程，不得丢消息，不得重复投递
2. **消息全覆盖** — 审批、Self-improvement review、工作轮状态、定时任务、后台任务、澄清、压缩提示，全部纳管
3. **单卡收敛** — 一轮 Agent 运行的所有输出收敛到同一张卡片，杜绝游离消息
4. **流式效果** — 保持 CardKit v2.0 客户端插值渲染的打字机体验
5. **可扩展** — 新增消息类型、新增渲染样式、新增平台不需要改动核心层

### 1.2 硬约束

- 运行在 Hermes Gateway 进程内，不引入独立进程、不引入 IPC、不监听端口
- 与 Hermes 源码的耦合必须收敛在单一适配层，且注入点数量最小化
- 插件不可用时，Hermes 必须能完整回落到原生行为
- 依赖飞书 CardKit v2.0（`streaming_mode`），这是流式效果的唯一来源，不可替代

### 1.3 明确不做

- 不做 sidecar 架构（论据见 01 文档 6.2）
- 不做跨进程签名鉴权体系（进程内不需要）
- 不做多 bot 多租户（首版单凭据，接口预留）
- 不自建飞书 WebSocket 连接（会与 Hermes 的连接重复消费事件）

## 二、既有问题的根因定位

用户提出的三个现象，根因各不相同，必须分开治理。

### 2.1 现象 A：审批 / review / 工作轮消息游离在卡片外

**根因**：这些消息与流式内容走的是**两条完全独立的发送通道**。

Hermes 源码中（`gateway/run.py`），流式内容通过 `agent.stream_delta_callback` 进入卡片，而其余消息各自直接调用适配器发送：

| 消息类型 | 发送出口 | 源码位置 |
|---|---|---|
| 自我改进 review | `ctx._status_adapter.send(...)` | run.py:6025 |
| 澄清提问 | `ctx._status_adapter.send_clarify(...)` | run.py:6154 |
| 危险命令审批 | `ctx._status_adapter.send_exec_approval(...)` | run.py:6326 |
| 额度 / 系统通知 | `self._runner._deliver_platform_notice(...)` | run.py:5979 |
| 状态提示（压缩、重试等） | `agent.status_callback` → `_status_callback_sync` | run.py:5955 |

HLS 只 hook 了 `background_review`，且做法是**延迟发送**（`defer_background_review`），本质上仍是独立消息，没有并入卡片。因此现象 A 在 HLS 上无法通过配置消除。

**关键机会**：上表五个出口中，有四个都收敛到同一个对象 `ctx._status_adapter`。**包装这一个对象，即可拦截绝大多数游离消息。**

置信度【确定】，依据为上述源码行号。

### 2.2 现象 B：卡片还在 thinking，新消息把卡片顶上去

**根因**：飞书 IM 是线性消息流，任何新消息都会把历史消息上推。这是平台固有行为，**无法从插件侧阻止**。

因此治理方向不是"阻止上推"，而是**减少上推源 + 补偿状态可见性**：

- 消除游离消息（治理 A）后，一轮运行只产生 1 条消息，上推源从 N 降到 1
- 卡片被上推后，用户仍需知道它的状态 → 转由 2.3 的机制承载

**不采用的方案**：主动重发卡片到会话底部。这会产生重复卡片、破坏历史可读性，且与"单卡收敛"目标直接冲突。

### 2.3 现象 C：切到其他会话后，看不出原会话任务是否完成

**根因**：卡片状态只在打开该会话时可见，会话列表层面无感知。

**治理机制**：飞书卡片的 `config.summary` 字段就是**会话列表的预览文本**，这是平台原生提供的跨会话状态通道。

HLS 当前的用法不足以支撑：流式卡的 summary 是静态常量 `Processing`（`cardkit/builder.py:445-448`），整个运行过程不更新；且 `header.enabled` 默认关闭，状态着色未启用。

**本设计的做法**：把 summary 提升为**一等状态通道**，随 turn 阶段实时更新，并默认开启 header 状态着色。详见 6.4。

## 三、核心架构决策

### 决策 1：运行时织入，不修改 Hermes 源码

> 本决策在 v1.0 定稿时经过一次重大修正。原方案是「把注入点从 15 个压到 2 个」，
> 验证过程中发现存在**完全不注入**的可行路径，遂改为主方案。完整论证见
> [03-升级韧性设计.md](03-升级韧性设计.md)。

**背景**：两个参考实现都走 AST 源码注入（HLS 15 处、HFC 17 组 patch）。但 Hermes
升级路径是 git reset（证据：`gateway/run.py:20-25` 注释中的 `git-reset landed new
code`），会把注入的 marker 块整体抹掉，导致**静默失效**——插件包还在、gateway 正常
跑、只是卡片不再出现，且日志无任何报错。

**决策**：改用运行时织入。利用 Python 数据描述符优先于实例 `__dict__` 的规则，在
`AIAgent` 类上安装描述符，拦截 Hermes 的回调装配：

```text
Hermes 执行 agent.stream_delta_callback = 原回调   (run.py:5953)
                  │
                  ▼
        AIAgent 类上的描述符 __set__ 被触发
                  │
                  ├─ 包装为「先喂卡片，再决定是否透传」
                  └─ 存入 instance.__dict__
                  │
                  ▼
        Agent 运行时读到的是包装后的回调
```

织入代码的执行时机由 Hermes 官方插件 entry point 提供。该 entry point 由 pip 写入
`site-packages`，**不在 Hermes 的 git 工作区内**，因此 git reset 不会影响它。

**可行性已验证**（每条均有源码行号支撑，置信度【确定】）：

- `AIAgent` 无 `__slots__`、实例有 `__dict__` — `run_agent.py:3282` 使用 `vars(self)`
- Gateway 会往 agent 实例挂任意属性 — `run.py:6013`、`run.py:6223`
- 回调以实例属性赋值装配 — `run.py:5953-6004` 连续 8 处
- `AIAgent` 可被 import 与 monkey-patch — `run_agent.py:17`、`run_agent.py:55`
- 数据描述符优先级 — Python 语言规范保证

**收益**：

| 维度 | 源码注入 | 运行时织入 |
|---|---|---|
| Hermes 升级后 | 必然失效 | 不受影响 |
| 失效可见性 | 静默 | 启动即报错 |
| 残留 | `.bak` + marker 块 | 零 |
| 与其他 patch 插件冲突 | 有 | 无 |
| 卸载 | 需先移除 marker | `pip uninstall` 即可 |

**降级预案**：保留最小源码注入（2 个注入点、事务化 manifest）作为 `--legacy-patch`
备用路径，仅在运行时织入被证明不可用时显式启用，不是默认。

### 决策 2：Adapter 实例方法织入，实现单卡收敛

**先说一个必须避开的陷阱。** 最直觉的做法是造一个代理对象替换 `ctx._status_adapter`，但**这个做法是错的**，会静默破坏审批功能。

Hermes 检测适配器能力时，查的是**类**而不是实例：

```python
# gateway/run.py:6323
if getattr(type(ctx._status_adapter), "send_exec_approval", None) is not None:
    ...  # 走飞书按钮审批
else:
    ...  # 降级为纯文本 /approve 指令

# gateway/run.py:6079 同样模式
if getattr(type(ctx._status_adapter), "register_post_delivery_callback", None) is not None:
```

如果替换成一个只实现 `__getattr__` 的代理类，`type(proxy)` 上并不存在 `send_exec_approval` 这个属性，检查返回 `None`，Hermes 会**认为飞书不支持按钮审批而降级为纯文本**——功能被静默削弱，且极难排查。

**正确做法：不换对象，只换实例上的方法（instance-level method binding）。**

```text
原 adapter 实例（类型、类属性全部不变）
   │
   ├─ 类上仍然有 send / send_clarify / send_exec_approval
   │     → getattr(type(adapter), ...) 检查照常通过 ✅
   │
   └─ 实例属性上绑定包装函数（实例属性优先级高于类属性）
         adapter.send              = wrapped_send
         adapter.send_clarify      = wrapped_send_clarify
         adapter.send_exec_approval= wrapped_send_exec_approval
              → 实际调用命中包装 ✅
```

Python 的属性查找顺序保证了这一点：实例 `__dict__` 优先于类 `__dict__`，而 `getattr(type(obj), ...)` 只看类。两个需求同时满足。

依据：`gateway/platforms/base.py:3011-3128` 显示 `BasePlatformAdapter.__init__` 中全部状态都是普通实例属性，对象未使用 `__slots__`，可安全绑定新属性。置信度【确定】。

**织入范围**（每个平台适配器只织入一次，用标记属性 `_hls_woven` 幂等保护）：

| 被织入方法 | 拦截后归属 | 未命中时 |
|---|---|---|
| `send(chat_id, message, metadata=...)` | NOTICE / REVIEW Segment | 调原方法 |
| `send_clarify(chat_id, question, choices, clarify_id, session_key, metadata)` | INTERACTION Segment | 调原方法 |
| `send_exec_approval(chat_id, command, session_key, description, metadata, ...)` | INTERACTION Segment | 调原方法 |

以上三个签名均取自 Hermes 的真实调用点（run.py:6025、6154、6326），不是推测。

**Turn 归属解析**：适配器是**平台级单例**，被所有会话共享，因此包装函数**不能闭包绑定某个 turn**。它必须在调用时用 `chat_id` / `session_key` 反查 Turn 注册表，找到当前活跃 turn；查不到就透传。这正是 L2 需要一个独立 Turn 注册表的原因。

**降级契约**：每个包装函数遵循同一规则 —— 无活跃卡片、卡片已终态、收纳抛异常，任一条命中都**立即调用原方法透传**，保证消息不丢。

### 决策 3：One Turn, One Card（单卡收敛）

一次 Agent 运行（turn）= 一张卡片。所有内容以 Segment 形式按到达顺序追加到这张卡片。

Segment 类型在 HLS 三种基础上扩展为六种：

| Segment | 来源 | 渲染形态 |
|---|---|---|
| `REASONING` | `reasoning_callback` / `interim_assistant_callback` | 可折叠面板（思考） |
| `ANSWER` | `stream_delta_callback` | 流式 markdown（打字机） |
| `TOOL` | `tool_progress_callback` | 可折叠面板（工具时间线） |
| `NOTICE` | `status_callback` / `notice_callback` / adapter.send | 灰色小字提示行 |
| `REVIEW` | `background_review_callback` | 带图标的提示块 |
| `INTERACTION` | `send_clarify` / `send_exec_approval` | 状态块（首版）→ 按钮（二期） |

**例外（保持独立卡片，不强行收敛）**：

- 定时任务（cron）结果 —— 不属于任何用户 turn，无宿主卡片
- 后台任务（`/background`）完成推送 —— 触发时原 turn 可能早已结束

这两类使用**独立完整卡片**（而非灰色文本），并携带来源标识与时间，属于设计内的合理独立，不是"游离"。

### 决策 5：Hermes 耦合面单层隔离

分层架构中，**只有 L0 桥接层允许出现 Hermes 相关的符号**。L1 及以上只认插件自定义的事件模型，因此 Hermes 升级的影响半径被限制在 L0。

**一条硬约束：任何模块的顶层都不得 `import gateway.run`。**

`gateway/run.py` 的模块体里就调用了 `get_plugin_auxiliary_tasks()`，它会触发 Hermes 的插件发现。在插件模块顶层 import 它会形成闭环：

```text
Hermes 加载本插件 → import 本插件模块 → import gateway.run
  → gateway.run 模块体触发插件发现 → 再次加载本插件
    → 本插件模块仍在初始化中，register() 尚未定义
      → Hermes 报 "has no register() function" 并在注册表记一条加载失败
```

外层加载最终会拿到完整模块并正常调 `register()`，但嵌套那几层留下的失败记录会让 `hermes plugins list` 误报。凡需借用 `gateway.run` 里的符号（如生命周期文案常量），一律**惰性导入 + 结果缓存**，把时机推到运行期第一次真正需要判定时——那时 `gateway.run` 早已 import 完毕。

L1 的 `events/normalize.py` 是唯一需要借 `gateway.run` 常量的地方（`is_lifecycle_notice`），它按此约束实现，并由一条 AST 静态测试守住整个包不再出现顶层 import。

这个缺陷只在「pip 安装 + 由 Hermes 插件加载器加载」的真实部署形态下出现：直接调 `bootstrap()` 的测试路径构不成闭环，所以它是靠真机安装才暴露的——也是「零真实流量」这个验证缺口兑现的第一笔代价。

### 决策 6：稳定性优先于功能完备

任何功能，如果其实现会引入不可控的失败面（跨进程、自建长连接、劫持 Hermes 内部状态机），一律降级为"只读展示"形态，而不是强行做完整交互。

具体体现：审批 / 澄清首版只做**状态收纳**（卡片内显示"等待审批"及内容），**保留 Hermes 原生的按钮卡片**继续承载交互。待飞书 card action 注册点验证通过后，二期再把按钮收进主卡。

**理由**：审批是安全边界。一个做错的审批交互（漏点、重复点、点了没生效）比"多一张原生卡片"严重得多。

### 决策 7：自愈层完全旁路，且用户配置永远优先

插件需要从运行中积累经验（哪类收纳在这套环境里总是失败、上次成功织入了什么），但这个能力本身不能成为新的失败面——**加一个自学习子系统正是往"耦合面小"的反方向走**，所以约束比功能更重要。

四条设计约束：

- **旁路化**：自愈层不被任何层反向依赖。它由编排层调用；桥接层的装配观测通过**依赖注入**（`weave.set_observer()`）单向上报，避免 L0 反向 import。整层可用 `selfheal.enabled: false` 关闭，关闭后行为与不带自愈时逐字一致
- **用户永远赢**：优先级严格为 **用户显式配置 > 学到的经验 > 内置默认**。这要求配置层能区分「用户写了 `true`」与「用户没写、默认是 `true`」，故新增 `Config.capture_explicit()` 返回三态（`True` / `False` / `None`）。用户写死的项即使连续失败一百次也继续尝试，插件只在报告里说明
- **不改用户的文件**：学习结果只落插件独占的状态目录，绝不回写 `~/.hermes/config.yaml`——那是用户的文件，偷改会与手工编辑冲突且不可预期
- **自修复止于参数**：只调整运行时行为（是否收纳某类消息），绝不自动改代码。涉及代码的判断只输出到 `doctor` 由人决定

**与熔断器的分工**：熔断器管「核心流式坏了怎么办」——答案、推理、工具面板失效意味着插件失去全部价值，全局退回原生是正确的。自愈层管「某一类收纳坏了怎么办」——只关掉那一类。只有失败跨越 3 类以上才判定为系统性故障（凭据、网络、权限），升级为全局熔断。

## 四、分层架构

```text
┌──────────────────────────────────────────────────────────────┐
│ L0  bridge/     桥接层 — 唯一接触 Hermes 的层                  │
│     ├─ plugin.py       官方 plugin 入口 register(ctx)          │
│     ├─ weave.py        AIAgent 描述符织入 + 启动自检 + 回滚     │
│     ├─ callbacks.py    回调包装逻辑（流式 / 工具 / 游离消息）    │
│     ├─ adapter.py      status_adapter 实例方法织入              │
│     └─ legacy_patch.py AST 注入降级预案（--legacy-patch 才启用）│
├──────────────────────────────────────────────────────────────┤

│     ├─ segments.py     Segment 模型与顺序管理                   │
│     ├─ tooltrack.py    工具调用追踪与脱敏                       │
│     └─ dispatcher.py   事件路由（EventKind → handler）          │
├──────────────────────────────────────────────────────────────┤
│ L3  render/     渲染层 — Segment → CardKit JSON                │
│     ├─ card.py         流式卡 / 完成卡 / 独立卡构建             │
│     ├─ elements.py     元素构建原语                            │
│     ├─ budget.py       元素预算与拆卡决策                       │
│     ├─ markdown.py     长文本切分、表格降级、图片解析           │

│ L4  transport/  传输层 — 飞书 API 与调度                        │
│     ├─ client.py       CardKit / IM API 封装（lark-oapi）       │
│     ├─ scheduler.py    节流、合并、序列号、重刷补偿             │
│     ├─ resilience.py   重试、熔断、错误码分类                   │
│     └─ guard.py        消息不可用保护                          │
├──────────────────────────────────────────────────────────────┤
│ 旁路  selfheal/  经验积累与精准降级（不被任何层依赖）            │
│     ├─ store.py        状态文件原子读写 + 类型校验              │
│     └─ healer.py       降级决策、指纹作废、试探恢复、报告        │
├──────────────────────────────────────────────────────────────┤
│ 横切  config.py  observability.py  cli.py                      │
└──────────────────────────────────────────────────────────────┘
```

**依赖方向严格单向**：L0 → L1 → L2 → L3 → L4，禁止反向依赖与跨层调用。L2 不得 import 任何飞书符号，保证领域逻辑可单测。`selfheal/` 只依赖 `observability`，由编排层驱动、经依赖注入接收 L0 的观测，因此可整层摘除。

## 五、核心数据模型

### 5.1 统一事件模型（L1）

所有消息源归一化为单一事件类型，这是扩展性的基石：

```python
class EventKind(StrEnum):
    TURN_STARTED     = "turn.started"
    TURN_COMPLETED   = "turn.completed"
    TURN_FAILED      = "turn.failed"
    TURN_ABORTED     = "turn.aborted"
    TURN_INTERRUPTED = "turn.interrupted"
    ANSWER_DELTA     = "answer.delta"
    REASONING_DELTA  = "reasoning.delta"
    TOOL_STARTED     = "tool.started"
    TOOL_COMPLETED   = "tool.completed"
    NOTICE           = "notice"            # 状态、压缩、重试、额度
    REVIEW           = "review"            # self-improvement
    CLARIFY_OPENED   = "clarify.opened"
    CLARIFY_CLOSED   = "clarify.closed"
    APPROVAL_OPENED  = "approval.opened"
    APPROVAL_CLOSED  = "approval.closed"
    CRON_DELIVERED   = "cron.delivered"
    BACKGROUND_DONE  = "background.done"

@dataclass(frozen=True)
class StreamEvent:
    kind: EventKind
    turn_key: str            # turn 归属键
    payload: Mapping[str, Any]
    at: float
```

**扩展契约**：新增一种消息类型 = 新增一个 `EventKind` + 一个 dispatcher handler + 一个 Segment 渲染分支。L0/L4 不动。

### 5.2 Turn 状态机（L2）

```text
        ┌─────────┐
        │  IDLE   │
        └────┬────┘
             │ TURN_STARTED
        ┌────▼─────┐
        │ CREATING │ ── 建卡失败 ──▶ ┌──────────┐
        └────┬─────┘                │ FALLBACK │ ─▶ 交还 Hermes 原生
             │ 建卡成功              └──────────┘
        ┌────▼──────┐
   ┌───▶│ STREAMING │◀──┐
   │    └────┬──────┘   │ CLARIFY_CLOSED / APPROVAL_CLOSED
   │         │          │
   │  CLARIFY_OPENED    │
   │  APPROVAL_OPENED   │
   │    ┌────▼──────┐   │
   └────│  WAITING  │───┘
        └────┬──────┘
             │ TURN_COMPLETED / FAILED / ABORTED / INTERRUPTED
        ┌────▼──────┐
        │ FINALIZING│ ── close_streaming + 全量重建 ──▶ ┌───────────┐
        └───────────┘                                  │ TERMINAL  │
                                                       └───────────┘
```

**关键规则**：

- `WAITING` 状态下**暂停 flush 但不封卡**，避免审批期间卡片被提前定格
- 只有 `TERMINAL` 允许抑制 Hermes 原生正文；`FALLBACK` 必须放行原生
- 状态迁移全部加锁，且只允许单向前进，禁止从终态回退

## 六、核心机制设计

### 6.1 流式渲染管线（保持 HLS 的三件套）

```text
answer delta ─▶ Segment.text 累加 + dirty
                     │
                     ▼  节流 100ms
              scheduler.flush()
                     │
        ┌────────────┴────────────┐
        ▼                         ▼
  结构性变更                  文本增量
  batch_update              stream_element
  (add_elements /           (单元素内容,
   partial_update)           sequence 递增)
        │                         │
        └────────────┬────────────┘
                     ▼
        飞书客户端按 print_frequency_ms=15
        逐字插值渲染 → 打字机效果
```

**必须保留的三个要素**（缺一则流式效果退化为跳变）：

1. 卡片经 `cardkit_create` 实体化，消息只引用 `card_id`
2. 卡片 config 声明 `streaming_mode: true` + `streaming_config.print_frequency_ms: 15`
3. 文本更新走 `cardkit_stream_element` 单元素增量，而非整卡替换

### 6.2 游离消息收纳（决策 2 的落地细节）

`CardBoundAdapter` 的拦截规则：

**`send(chat_id, message, metadata=...)`**

1. 查当前 turn 是否有活跃卡片 → 无则透传原方法
2. 对 message 做模式识别（复用 Hermes 自身的状态常量，见下）→ 归类为 NOTICE 或 REVIEW
3. 追加为对应 Segment，触发 flush
4. **返回一个伪造的成功结果**，让 Hermes 认为已投递
5. 任一步异常 → 透传原方法

**模式识别的证据来源**：不自造正则，直接复用 Hermes 已导出的常量。`gateway/run.py:51-60` 导入了 `COMPACTION_STATUS`、`IDLE_COMPACTION_STATUS_TEMPLATE`、`PRE_API_COMPRESSION_STATUS_TEMPLATE` 等压缩状态模板；`run.py:119-152` 的 `_TELEGRAM_NOISY_STATUS_RE` 已经枚举了全部"应留在日志、不该进聊天"的状态文案。**直接引用这些常量做分类，比自写正则稳定得多。**

**`send_clarify(...)` / `send_exec_approval(...)`**

首版策略（决策 6）：

1. 先向卡片追加 `INTERACTION` Segment，渲染为"⏳ 等待澄清 / 等待审批"状态块，附问题或命令摘要
2. Turn 状态迁移到 `WAITING`，暂停 flush
3. **随后仍调用原方法**，让 Hermes 原生按钮卡正常发出，交互不受影响
4. 用户操作完成后（`CLARIFY_CLOSED` / `APPROVAL_CLOSED`），Segment 更新为结果态，Turn 回到 `STREAMING`

这样卡片内**完整记录了审批发生过、内容是什么、结果如何**，同时零风险。

### 6.3 拦截安全阀

拦截 Hermes 的消息发送是有风险的操作，必须有三重保护：

1. **白名单拦截**：只拦截明确识别的方法，未知方法一律 `__getattr__` 透传
2. **异常即透传**：拦截逻辑任何异常都 fallthrough 到原方法，且异常只记日志
3. **全局熔断**：连续 N 次收纳失败后，代理自动进入 bypass 模式，本进程后续全部透传，直到下次 gateway 重启

### 6.4 状态可见性三通道（治理现象 C）

| 通道 | 载体 | 更新时机 | 用户可见位置 |
|---|---|---|---|
| 会话列表摘要 | `card.config.summary` | 每次阶段切换 | 飞书会话列表预览行 |
| 卡片状态条 | `card.header` + template 着色 | 每次状态迁移 | 卡片顶部 |
| 终态标记 | footer + header 定格 | TERMINAL | 卡片底部 |

**summary 文案设计**（随阶段动态更新，这是与 HLS 的关键差异）：

- `CREATING` → `⏳ 已收到，正在启动…`
- `STREAMING`（无工具）→ `💭 思考中…`
- `STREAMING`（有工具）→ `🛠️ 正在执行：<工具名>（第 N 步）`
- `WAITING` → `⏸️ 等待你的确认`
- `TERMINAL` 成功 → `✅ 已完成 · <答案前 60 字>`
- `TERMINAL` 失败 → `❌ 执行失败`
- `TERMINAL` 用户停止 → `⏹️ 已停止`
- `TERMINAL` 被新消息接续 → `⏭️ 已中断 · 新消息已接续`
- `TERMINAL` 超时收尾 → `⏱️ 已超时收尾`

如此，用户在会话列表即可判断每个会话的任务是否跑完，无需逐个点开。`header.enabled` 默认改为 `true`（HLS 默认 `false`）。

### 6.5 元素预算与拆卡

沿用 HLS 已验证的策略（阈值 180、footer 预留 2、tool step 边界拆分、建卡失败降级），新增两点：

- NOTICE / REVIEW Segment 纳入预算估算（各计 1~2 个元素）
- 拆卡时旧卡 summary 更新为 `📄 已归档（续见下一张卡）`，避免会话列表显示误导

### 6.6 降级与 fail-open 三态

任何投递必须落到三态之一，禁止二值判断：

| 状态 | 含义 | 处置 |
|---|---|---|
| `TAKEN` | 卡片已确认接管 | 抑制 Hermes 原生输出 |
| `DECLINED` | 明确未接管 | 放行 Hermes 原生输出 |
| `UNKNOWN` | 结果不确定 | **放行原生**，卡片侧标记异常 |

`UNKNOWN` 一律按放行处理：宁可用户看到一次重复，也不能丢消息。这是与 HFC 的重要差异 —— HFC 为消除重复引入了 native handoff 三阶段 ACK 协议，复杂度极高却仍有"uncertain"分支。本设计直接选择"重复优于丢失"，用简单性换稳定性。

## 七、稳定性设计

### 7.1 失败面对比

| 失败面 | HFC（sidecar） | 本设计（进程内） |
|---|---|---|
| 独立进程崩溃 | 有 | 无 |
| 端口占用 / 绑定失败 | 有 | 无 |
| HTTP 超时 / 连接拒绝 | 有 | 无 |
| 签名密钥不一致 | 有 | 无 |
| 进程间状态不同步 | 有 | 无 |
| PID 复用误杀 | 有 | 无 |
| systemd 服务异常 | 有 | 无 |
| Hermes 源码 patch 漂移 | 有（17 组） | 有（2 处） |
| 飞书 API 故障 | 有 | 有 |

进程内架构直接消除 7 类失败面，剩余 2 类中 patch 漂移面收窄到 2 处。

### 7.2 并发与线程安全

Hermes 的回调来自**多个线程**：`agent` 运行在 worker 线程，gateway 运行在 asyncio 事件循环（源码中大量使用 `safe_schedule_threadsafe` 跨线程调度，见 run.py:5978、6024、6153）。

因此：

- Turn 注册表读写加 `threading.Lock`
- Segment 追加在锁内完成，flush 调度在锁外
- 所有飞书 API 调用统一经事件循环执行，禁止在 worker 线程直接发起
- 每个 Turn 的 `sequence` 单调递增且只在事件循环内自增，避免 CardKit 乱序

### 7.3 资源边界

| 资源 | 上限 | 回收策略 |
|---|---|---|
| 活跃 Turn 数 | 256 | LRU + TTL（默认 600s）双重回收，**回收活跃 turn 必先收卡** |
| 待收卡队列 | 64 | 超出丢最旧的并计数（防泄漏机制自身不能变成泄漏点） |
| 单 Turn 工具步数 | 128 | 超出丢弃并标注 |
| 单 Segment 文本 | 32 KB | 超出切分为新 Segment |
| 卡片元素数 | 180 | 自动拆卡 |
| 待发 NOTICE 队列 | 64 | 超出合并为"N 条提示已折叠" |

**回收活跃 turn 必须先收卡**，这条不变式是从参考实现的线上故障反推出来的：
HLS 按 `created_at` 剪枝，600 秒后直接丢掉 turn 对象，而它的卡片此刻正带着
loading 动画——结果是卡片永远转圈。本设计里注册表处于 L2 领域层，不能自己
发起飞书调用，因此把被摘除的活跃 turn 放进 `take_pending_finalize()` 队列
交还编排层，由 `finalize_detached()` 异步收尾。取走点有两处：`create()` 之后
（容量淘汰）与空闲守护每轮扫描之后（TTL 回收）。

回收类收卡在卡片上呈现为「⏱️ 已超时收尾」并附一条说明性提示，**刻意不渲染成
「✅ 已完成」**：真相是「卡片停止跟踪了」，而任务本身可能仍在运行。把它显示为
完成态比不收卡更误导——用户会以为任务成功了。

### 7.4 安装器事务化（补 HLS 的短板）

HLS 只做单文件 `.bak` 备份，无事务、无块外改动检测。本设计要求：

1. **manifest 文件**记录每个 target 的路径、注入前 SHA-256、注入后 SHA-256、marker 名、插件版本
2. **两阶段提交**：全部 target 校验通过 → 全部写入；任一失败 → 全部回滚
3. **块外改动检测**：卸载前比对当前文件与 manifest 记录的注入后 hash，不一致则拒绝自动卸载并提示人工介入
4. **原子写入**：临时文件 + `os.replace`（沿用 HLS 已有实现）
5. **幂等**：重复 install 先清理旧 marker 再注入，不叠加

### 7.5 可观测性

- 结构化日志：每条带 `turn_key`、`state`、`seq`、`elapsed`
- 内存指标：turn 数、flush 次数、API 调用数与错误码分布、拦截命中数、熔断次数
- `status` 命令输出：注入状态、配置、凭据、活跃 turn 数、最近错误
- 敏感信息脱敏在**写日志前**完成，复用 HLS 的 `redact_inline_secrets`

## 八、扩展性设计

### 8.1 三个扩展点

**扩展点 1 · 新消息类型**
新增 `EventKind` → 在 `dispatcher` 注册 handler → 在 `render/card.py` 增加 Segment 分支。不触碰 L0/L4。

**扩展点 2 · 新渲染样式**

**扩展点 3 · 新平台**
L2 领域层不含飞书符号。理论上替换 L3/L4 即可支持其他平台。首版不实现，但分层边界为此预留。

### 8.2 配置结构

```yaml

  header:
```

| 委派子任务 | `SubagentLifecycleService.launch` / `_run` | 卡内 NOTICE | 🧩 提示块（启动含目标与模型，终态含结果摘要） |
| 订阅额度用量 | `agent.account_usage` | 卡内 footer | `usage` 字段（默认关闭，需显式开启） |
| 定时任务结果 | `cron/scheduler.py` | 独立卡片 | 完整卡片 + 任务名/时间 |
| 后台任务完成 | `bg deliver` | 独立卡片 | 完整卡片 + 触发摘要 |
| 用户 `/stop` | `AIAgent.interrupt(hard_cancel=True)` | 卡内终态 | 定格为「已停止」（红） |
| 新消息打断 | `AIAgent.interrupt(message=...)` | 旧卡终态 | 定格为「已中断 · 新消息已接续」（橙），新消息自行建卡 |

**关于 gateway 关闭通知的例外**：单卡收敛的原则是「接管即抑制原生」，这里是唯一刻意的例外。该通知在 `stop()` 最开头发出，此刻事件循环随时会停，而卡片更新要经过 100ms 节流 + 一次飞书 API 往返，协程很可能来不及执行。抑制原生输出就会让这条关键信息彻底消失——违反「消息永不丢失」这条更高优先级的原则。因此这一类走「卡片记一份、原生照发」。判定短语从 Hermes 的 `_INTERRUPT_REASON_GATEWAY_SHUTDOWN` / `_INTERRUPT_REASON_GATEWAY_RESTART` 借用（与复用压缩状态常量同一手法），Hermes 改文案时自动跟随。

**`_send_with_retry` 为何无需单独织入**：它内部第一步就是 `await self.send(...)`（`gateway/platforms/base.py:5551`），因此织入 `send` 已经覆盖了经它发出的全部消息。这是实例方法织入相对 AST 注入的又一个好处——**拦在调用链的汇聚点上，上游有多少入口都不必逐个枚举**。

### 阶段 1 · 骨架（可运行的最小闭环）

L4 传输层 + L3 基础渲染 + L2 Turn 状态机 + L0 两个注入点，跑通「答案流式 + 终态收卡」。验收标准：打字机效果与 HLS 一致。

### 阶段 2 · 消息收纳

adapter 代理 + NOTICE / REVIEW Segment + 安全阀熔断。验收标准：一轮运行只产生 1 条飞书消息。

### 阶段 3 · 状态可见性

summary 三通道 + header 着色 + 拆卡 summary。验收标准：会话列表可判断任务是否完成。

### 阶段 4 · 交互与独立卡

澄清 / 审批状态收纳、cron / background 独立卡、中断与打断处理。

### 阶段 5 · 工程化

安装器事务、manifest、诊断命令、指标、单元测试。

### 阶段 6（二期） · 按钮内联

验证 V3 通过后，把审批 / 澄清按钮收进主卡片。

## 十一、风险登记

| 风险 | 等级 | 说明 | 缓解 |
|---|---|---|---|
| 拦截 adapter 导致消息丢失 | **高** | 收纳失败且未透传则消息永久丢失 | 异常即透传 + 熔断 bypass + 三态语义（7.1、6.3、6.6） |
| Hermes 升级导致注入点失效 | 中 | 锚点漂移 | 注入点收窄到 2 处 + AST 校验 + verify 明确报错 |
| 审批交互被破坏 | **高** | 安全边界 | 首版不接管按钮，只做状态收纳（决策 6） |
| CardKit 频控（230020） | 中 | 高频 flush 触发 | 100ms 节流 + 长空闲批量 + 频控码静默重试 |
| 卡片元素超限 | 中 | 长会话 | 预算估算 + 自动拆卡（6.5） |
| 多线程竞态 | 中 | 回调跨线程 | 注册表加锁 + API 调用统一入事件循环（7.2） |
| 与已安装的 HLS 冲突 | 中 | 当前 Hermes 已被 HLS patch（run.py:5989、6055、6178 可见其 marker） | install 前强制检测并要求先卸载 HLS |

## 十二、与两个参考插件的关系总结

- **继承自 HLS**：CardKit v2.0 流式三件套、Segment 扁平模型、元素预算与拆卡、节流器、消息不可用保护、工具脱敏、双语 i18n、原子写入
- **继承自 HFC（思想而非代码）**：安装器事务化、兼容性证据化诊断、fail-open 三态语义、系统提示卡片化
- **两者都没有的原创设计**：单点接管（2 个注入点）、Adapter 代理收纳游离消息、Turn 状态机含 WAITING 态、状态可见性三通道、拦截熔断安全阀
- **明确抛弃**：sidecar 架构、跨进程签名体系、native handoff 三阶段 ACK、散点多注入

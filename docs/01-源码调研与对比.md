## 二、HFC 核心设计：sidecar-only 架构

### 2.1 架构形态

HFC 把飞书卡片的全部逻辑放在一个**独立进程**（sidecar）里，Hermes 进程内只保留最小 hook，两者通过本机 HTTP 通信。

```text
Hermes Gateway 进程
  ├─ gateway/run.py            ← marker 包裹的生命周期 hook
  ├─ gateway/platforms/base.py ← Hermes 0.19+ 的精确终态投递 hook
  └─ hermes_feishu_card.hook_runtime
         │  HTTP POST（签名 / fail-open）
         ▼
Sidecar 进程（hermes_feishu_card.server）
  ├─ delivery policy 判定
  ├─ CardSession 状态机
  ├─ render → 卡片 JSON
  └─ FeishuClient → 飞书 OpenAPI
```

依据：`docs/architecture.md` 第 7–17 行的链路图，以及 `hook_runtime.py:64` 的 `DEFAULT_EVENT_URL = "http://127.0.0.1:8765/events"`。

### 2.2 卡片投递机制（关键）

`feishu_client.py` 全文只提供三个对外方法：

- `send_card()` → `POST /im/v1/messages` 或 `POST /im/v1/messages/{id}/reply`，`msg_type` 固定为 `interactive`
- `update_card_message()` → `PATCH /im/v1/messages/{id}`，请求体是 `{"content": <整张卡片 JSON 序列化>}`
- `send_text_message()` → 纯文本兜底

**该文件不包含任何 CardKit 接口。** 没有 `/cardkit/v1/cards`，没有流式元素更新，没有流式模式开关。每一次内容变化，都是把整张卡片重新序列化后整体 PATCH 覆盖。

依据：`hermes_feishu_card/feishu_client.py:158-277`。置信度【确定】。

### 2.3 节流参数

`config.py` 的 `DEFAULT_CONFIG["card"]` 段：

- `max_wait_ms: 800` — delta 最大等待
- `max_chars: 240` — 字符阈值触发提前 flush
- `flush_interval_ms: 200` — 刷新间隔
- `final_drain_timeout_ms: 900` — 终态前排空

`README.md` 另外给出三个环境变量，默认 `DELTA_COALESCE_MS=250`、`DELTA_COALESCE_CHARS=600`、`MAX_PENDING=128`。

也就是说，**用户可见的更新频率上限约为每秒 4~5 次整卡替换**。

依据：`hermes_feishu_card/config.py:33-54`、`README.md:174-177`。置信度【确定】。

### 2.4 交互闭环的实现代价

HFC 的 approval / clarify 按钮闭环，必须跨越进程边界，其链路为：

1. 飞书按钮点击 → Hermes 进程内的飞书 WebSocket 长连接收到 card action
2. hook 转发到 sidecar 的 `POST /card/actions`
3. sidecar 判定后，反向 POST 回 Hermes 进程内的 `RuntimeInteractionListener`
4. 该监听器 resolve Hermes 原生的 pending future，Agent 继续执行

第 3 步的监听器是一个**在 Hermes 进程内临时启动的 loopback HTTP 服务**：绑定 `127.0.0.1:0`（随机端口）、32 并发上限、0.5 秒 socket 超时、8 KB body 上限，并强制 HMAC 签名 + 时间戳 + nonce 防重放。

依据：`runtime_interaction_transport.py:19-130`。置信度【确定】。

这一整套机制（含 `event_auth.py` 的五套签名域、`operations_transport.py`、`native_handoff.py`）**全部是跨进程通信的代价**，不是业务功能本身。这是后续架构选型的关键论据。

### 2.5 官方 plugin 机制的能力边界

`hermes_plugin_runtime.py:31-36` 给出了 Hermes 官方插件机制暴露的全部 lifecycle hook：

```python
OFFICIAL_HOOKS = (
    "pre_llm_call", "post_llm_call", "on_session_end",
    "on_session_reset", "on_session_finalize", "pre_tool_call",
    "post_tool_call", "pre_approval_request", "post_approval_response",
    "subagent_start", "subagent_stop",
)
```

**这 11 个 hook 中不存在任何流式增量事件**：没有 `answer.delta`，没有 `thinking.delta`，没有消息级的 started/completed。

这解释了 HFC v4.3 为何必须采用 Hybrid 方案 —— `docs/architecture.md:19` 明确写到，官方 plugin hook 之外仍需「17 个精确 patch group 补齐 hook call-site 未提供的 ingress、delta、interaction、terminal、cron 与 exact Base delivery 证据」。

**推论：任何要做流式打字机效果的插件，都无法只靠官方 plugin 机制，必须做源码注入。** 置信度【确定】。

## 三、HLS 核心设计：进程内 + AST 注入

### 3.1 架构形态

HLS 没有独立进程，全部逻辑运行在 Hermes Gateway 进程内，通过 AST 注入把 hook 调用写进 Hermes 源码。

```text
Hermes Gateway 进程
  ├─ gateway/run.py       ← 14 处 marker 注入
  ├─ cron/scheduler.py    ← 1 处 marker 注入
  └─ hermes_lark_streaming
         ├─ patch.py       ← hook 函数入口（薄层，只做 enabled 检查 + 转发）
         ├─ controller.py  ← 单例控制器，管理多消息卡片生命周期
         ├─ streaming/     ← segment 模型、节流、拆卡、工具追踪
         ├─ cardkit/       ← schema 2.0 卡片构建、i18n、markdown 处理
         └─ feishu.py      ← lark-oapi SDK 封装
```

依据：`patcher.py:23-56`、`README.md:180-193`。

### 3.2 注入点清单

`patcher.py` 定义 15 个 marker 块（`gateway/run.py` 14 个 + `cron/scheduler.py` 1 个）：

| Hook | 注入锚点 | 用途 |
|---|---|---|
| `NORMALIZE` | `_handle_message` 中 `source = event.source` 后 | 修正飞书引用消息的虚假 thread_id |
| `START` | `_handle_message_with_agent` 函数开头 | 建会话 + 发占位卡 |
| `COMPLETE` | `_already_sent = bool(` 前 | 终态收卡，并接管 `already_sent` |
| `FOLLOWUP_COMPLETE` | `was_interrupted = result.get("interrupted")` | 排队追问的边界收卡 |
| `FOLLOWUP_RESULT` | `return _preserve_queued_followup_history_offset(...)` | 回传最深层追问 id |
| `TOOL` | `progress_callback` 函数体 | 工具开始/结束 |
| `ANSWER` | `_stream_delta_cb` 函数体（**可能多处**） | 答案增量 |
| `THINKING` | `_interim_assistant_cb` 函数体 | 思考增量 |
| `REASONING` | `agent.reasoning_config = reasoning_config` 后 | 挂原生 reasoning 回调 |
| `BACKGROUND_REVIEW` | `agent.background_review_callback = _bg_review_send` 后 | 延迟自我改进通知 |
| `ABORT` | `Discarding stale agent result` 后的 `return None` | 陈旧结果丢弃 |
| `STOP` | `_interrupt_and_clear_session(invalidation_reason="stop_command")` 后 | `/stop` 终止 |
| `INTERRUPT` | `Restart typing indicator so the user sees activity` | 新消息打断旧消息 |
| `BG_DELIVER` | `images, text_content = adapter.extract_images(response)` 后 | 后台任务卡片推送 |
| `CLARIFY` | `agent.clarify_callback = _clarify_callback_sync` 后 | clarify 前后切卡 |
| `CRON_DELIVER` | `cron/scheduler.py` 的 `delivered = False` 后 | 定时任务卡片推送 |

**注意 `ANSWER` 的特殊性**：`_inject_all` 用 `_find_func_bodies`（复数）查找**所有** `_stream_delta_cb` 定义并逐个注入，`is_fully_patched` 也按实际数量校验。这说明 Hermes 存在多个流式回调定义点，漏注入任何一个都会导致部分场景不流式。

依据：`patcher.py:811-867`、`patcher.py:715-724`。置信度【确定】。

### 3.3 CardKit v2.0 流式三件套（核心机制）

HLS 流式效果的实现由三个要素共同构成，缺一不可：

**要素一：CardKit 实体化卡片**

卡片不再是消息的附属内容，而是一个独立的、有 `card_id` 的服务端实体：

```python
card_id = await client.cardkit_create(card)              # POST /cardkit/v1/cards
msg_id  = await client.reply_card_by_id(anchor, card_id) # 消息只引用 {"type":"card","data":{"card_id":...}}
```

后续所有更新针对 `card_id`，与消息本身解耦。

**要素二：元素级增量更新**

```python
await client.cardkit_stream_element(card_id, element_id, content, sequence=n)
```

对应 `PUT /cardkit/v1/cards/{card_id}/elements/{element_id}/content`。**只推送单个元素的文本内容**，不重传整张卡片结构。`sequence` 单调递增，服务端据此保序。

**要素三：客户端插值渲染（决定性）**

创建卡片时，卡片 JSON 里带上流式配置：

```json
{
  "schema": "2.0",
  "config": {
    "streaming_mode": true,
    "streaming_config": {
      "print_frequency_ms": {"default": 15},
      "print_step": {"default": 1},
      "print_strategy": "fast"
    }
  }
}
```

**打字机动画是飞书客户端本地渲染的**：客户端收到一段新文本后，按 15 毫秒 1 个字符的节奏自行"打"出来，与服务端推送频率完全解耦。

依据：`cardkit/builder.py:434-454`、`feishu.py:233-311`。置信度【确定】。

结构性变更（新增元素、更新工具面板）走另一条通道 `cardkit_batch_update`（`add_elements` / `partial_update_element`），与文本流式通道分离。终态用 `cardkit_close_streaming` 关流 + `cardkit_update` 全量重建。

### 3.4 Segment 扁平模型

HLS 不去推断"第几轮对话"，而是把内容拉平成一个按事件到达顺序排列的 `Segment` 列表，每个 segment 是 `REASONING` / `ANSWER` / `TOOL` 三者之一：

- 同类型连续到达 → 追加到最后一个 segment，标记 `dirty`
- 类型切换 → 新建 segment，并终结前一个 reasoning 的耗时

每个 segment 持有自己的 `el_id`（卡片元素 id），`created` 标记是否已在卡片上创建，`dirty` 标记文本是否待推送。flush 时分两步：先 `batch_update` 处理结构性变更（创建元素），再对 dirty 的文本 segment 逐个 `stream_element`。

依据：`streaming/segments.py:48-165`、`streaming/controller.py:173-347`。

这个模型的价值在于：**多轮"思考→工具→回答→再思考"的交错过程能按真实顺序还原**，不需要维护复杂的轮次状态机。

### 3.5 元素预算与自动拆卡

飞书单卡元素硬上限 200。HLS 设阈值 `ELEMENT_THRESHOLD = 180`，预留 `FOOTER_RESERVE = 2`，并对每类 segment 做静态估算（reasoning 4 个元素、answer 1 个、tool 面板按 step 逐项累加 3~7 个）。

超限时的处理顺序：

1. 先尝试在 tool step 边界内部拆分（`find_tool_split_offset` 从后往前找最大可容纳切点）
2. 仍超限 → 拆卡：先 flush 待发 actions，创建新卡，封印旧卡（`close_streaming` + 全量 `update`），新卡 `sequence` 从 1 重新计数
3. 建新卡失败 → `split_disabled = True` 降级，继续写当前卡（宁可超限报错，不中断输出）

依据：`streaming/segment_helper.py:18-69`、`streaming/controller.py:583-632`。

### 3.6 节流策略

`FlushController` 三档：

- 距上次刷新 ≥ 100 ms（`CARDKIT_MS`）→ 立即 flush
- 距上次刷新 > 2 s（`LONG_GAP_MS`）→ 延迟 300 ms 再 flush，攒一小批让内容更完整
- 仍在窗口内 → 延迟到窗口边界

并带互斥（`_flush_in_progress`）与补偿重刷（`_needs_reflush`），保证 flush 期间到达的增量不丢。

依据：`streaming/flush.py:13-141`。

### 3.7 其他工程细节

- **消息不可用保护**：`UnavailableGuard` 捕获 231003 / 230011 / 1000023 三个终态错误码，消息被删/撤回后立即终止 pipeline 并写入 30 分钟 TTL 缓存，避免对已删消息持续调用 API
- **工具展示脱敏**：`tooluse.py` 内置 13 类工具描述符（图标 + 标题 + 清洗器），命令类做 `key=secret` / `Authorization` / `--flag secret` 三重正则脱敏，路径类只保留 basename
- **降级契约**：CardKit 建卡失败 → `_mark_text_fallback_needed` → `on_message_needs_text_fallback` 让 Gateway 撤销 `already_sent`，回落到 Hermes 原生文本，**不吞消息**
- **双语**：卡片文本走 `i18n_content`，由飞书客户端按用户语言自动切换，不在服务端判断

## 四、流式效果差异的根因分析

这是本次调研最核心的结论。差异由三层叠加造成，但**权重极不均衡**。

### 4.1 第一层：更新粒度（重要）

- HFC：每次更新 = 整张卡片 JSON 重新序列化 + `PATCH /im/v1/messages/{id}`
- HLS：每次更新 = 单个元素的文本 + `PUT .../elements/{id}/content`

整卡 PATCH 会触发飞书客户端对整张卡片重新布局渲染，视觉上是**整块闪烁刷新**；元素级更新只影响一个 markdown 元素。

### 4.2 第二层：客户端插值渲染（决定性）

这是根本差异。

- HLS 的卡片声明了 `streaming_mode: true` 与 `print_frequency_ms: 15`，飞书客户端会把收到的文本**按 15 毫秒 1 字的节奏自行播放**。哪怕服务端 500 毫秒才推一次、一次推 200 个字，用户看到的仍然是连续 3 秒的平滑打字。
- HFC 没有这个配置，客户端收到什么就立刻显示什么。服务端 250 毫秒推一次，用户就看到每秒 4 次的整块跳变。

**结论：HFC 的「流式效果不明显」不是节流参数没调好，而是根本没有启用飞书的流式渲染模式。** 把 `DELTA_COALESCE_MS` 从 250 调到 50，只会把每秒 4 次跳变变成每秒 20 次跳变（且大概率触发 API 频控 230020），依然不是打字机。

依据：`cardkit/builder.py:437-448` 与 `feishu_client.py` 全文无 CardKit 调用的对照。置信度【确定】。

### 4.3 第三层：节流参数（次要）

| 维度 | HFC | HLS |
|---|---|---|
| 常规节流 | 200~250 ms | 100 ms |
| 字符阈值 | 240 / 600 字符 | 无字符阈值 |
| 长空闲策略 | 无 | > 2 s 后延迟 300 ms 批量 |
| 客户端播放 | 无 | 15 ms/字 |

### 4.4 量化对照

同样一段 600 字的回答，模型 3 秒生成完毕：

- **HFC**：约 12~15 次整卡 PATCH，用户看到十余次整块刷新，每次跳出约 40~50 字
- **HLS**：约 30 次元素级推送，客户端按 15 ms/字 播放，用户看到约 9 秒的连续打字（播放时长由字数决定，可长于生成时长）

## 五、优缺点对比

### 5.1 HFC 的优点

- **功能面最完整**：approval / clarify 按钮交互、`/model` 两级选择、`/resume` 会话选择器、slash 命令独立卡、系统提示卡片化、Codex 配额展示、附件摘要、cron 与 background 投递路由
- **多租户能力**：多 bot 注册（`bots list|show|add|remove|test`）、多 profile、按会话精确绑定原生投递（`bindings.native_chats`）
- **运维体系成熟**：`doctor --explain` 输出版本来源 / hook 策略 / 兼容性 / 锚点建议，`repair` / `restore` / `uninstall` / `smoke-feishu-card` 覆盖常见故障
- **安装器安全模型严谨**：manifest v2 事务把多个 patch target 的 backup / write / restore 纳入同一事务，块外改动 fail-closed
- **Hermes 版本兼容矩阵广**：0.13 至 0.20 均有兼容策略，版本 metadata 缺失时用可验证锚点兜底
- **Python 3.9+**，依赖仅 `aiohttp` + `PyYAML`，不绑定飞书官方 SDK

### 5.2 HFC 的缺点

- **流式效果差**：根因见 4.2，属架构级缺陷，非参数可调
- **复杂度失控**：sidecar 架构衍生出五套签名域、事件鉴权、native handoff 三阶段协议、runtime 心跳、delivery policy 双端执行、loopback interaction listener。这些代码量在整个项目中占比很高，却**不产生任何用户可见价值**，只为跨进程通信的正确性与安全性服务
- **运维负担**：多一个常驻进程要管（启停、健康检查、systemd user service、PID 复用防误杀），多一个故障面
- **端到端延迟叠加**：Hermes hook → HTTP → sidecar → 飞书 API，比进程内多一跳本机网络往返与 JSON 序列化
- **升级脆弱**：17 个精确 patch group 依赖 Hermes 源码 hash / slice 匹配，Hermes 升级后需要重新验证甚至等待插件更新
- **维护门槛高**：README 的版本历史里，大量条目是在修 sidecar 架构自身引入的问题（重复投递、投递结果不确定、卡片 owner 冲突、ACK 时序）

### 5.3 HLS 的优点

- **流式效果最好**：CardKit v2.0 三件套完整落地，客户端插值渲染
- **架构简洁**：进程内直连，无 IPC、无签名、无端口、无独立进程
- **Segment 扁平模型优雅**：多轮交错内容按真实顺序还原，无需轮次状态机
- **元素预算与拆卡完备**：接近 200 元素上限时自动按语义边界拆卡，旧卡封存数据完整
- **降级契约清晰**：建卡失败让位给 Gateway 原生文本，不吞消息
- **工程细节扎实**：消息删除保护、工具脱敏、双语 i18n、原子写入、幂等 patch
- **代码规模可控**：核心逻辑集中，`ruff` + `mypy` 严格模式（`disallow_untyped_defs`）

### 5.4 HLS 的缺点

- **无任何交互能力**：没有 approval / clarify 按钮，没有 slash 命令卡，用户仍需手工回文本
- **无多 bot / 多 profile**：单一凭据，`Config` 只读一份 `config.yaml`
- **无诊断运维体系**：`status` / `verify` 输出极简，没有 `doctor`，没有健康检查，没有修复建议
- **兼容性策略薄弱**：`_ANCHOR_CHECKS` 只有 9 条字符串锚点，Hermes 一改就 `Incompatible`，且**注入点定位失败即硬失败**（`patcher.py:840` 明确抛错而非跳过）
- **安装器无事务**：只做 `.hermes_lark.bak` 单文件备份，无 manifest，无跨文件事务，无块外改动检测
- **Python 3.11+**，且强依赖 `lark-oapi` SDK
- **无消息级投递策略**：不能按会话选择走原生还是走卡片
- **无附件 / 媒体处理**：只有 markdown 图片解析，没有文件、TTS、媒体回答的收束逻辑

### 5.5 HLS 的一个可复现线上故障：卡片永远转圈

这一条单独列，因为它是本项目一处设计决策的直接来源。

**症状**（用户实拍）：一张卡片里堆着 9 个空的「💭 思考了 X.Xs」折叠面板，正文
完全空白，loading 动画持续数小时不停。

**根因**：HLS 的 turn 剪枝按 `created_at` 计时（`controller.py:692`，默认 600
秒）。一个跑得久的任务在 10 分钟后会被剪掉——**注意它的 `updated_at` 可能就在
一秒前**，任务其实活得好好的。turn 对象一旦被丢弃：

1. 后续 delta 找不到 turn，内容无处可去 → 正文永远空白
2. 没有任何代码负责给那张卡片收尾 → loading 永远转
3. 新的思考事件又建新 turn 新面板 → 空面板越堆越多

**两处差别决定了本插件不会这样**：

| 维度 | HLS | 本插件 |
|---|---|---|
| 剪枝计时基准 | `created_at`（任务活着也会被剪） | `updated_at`（只剪真正没动静的） |
| 剪枝碰到活跃 turn | 直接丢对象 | 先入队交还编排层强制收卡（见 02 文档 7.3） |
| 兜底顺序 | 无兜底 | 空闲守护 90 秒先收卡，早于 600 秒 TTL |

第二行是从这个故障反推出的不变式：**回收活跃 turn 必须先收卡**。它同时覆盖了
本插件自己的 LRU 淘汰路径——那条路径原本也只打日志就丢对象，是同一个形状。

## 六、选型结论

### 6.1 结论

**新插件以 HLS 为架构基座，从 HFC 逐项移植功能，不移植 sidecar 架构。**

### 6.2 依据

1. **流式效果是不可让步的核心诉求，而它只能由 CardKit v2.0 + `streaming_mode` 提供。** HLS 已完整落地这条链路并经真实使用验证；从 HFC 改造需要重写整个投递层，等价于重做 HLS。
2. **HFC 的功能优势与其 sidecar 架构无关。** approval 交互、多 bot、doctor 诊断都是业务能力，与"逻辑跑在哪个进程"正交。移植功能不需要移植架构。
3. **进程内架构让交互闭环大幅简化。** HFC 为跨进程回填 pending future 所建的 loopback listener + HMAC 签名 + 随机端口 + 并发控制，在进程内架构下**全部不需要**：直接持有 future，直接 resolve。
4. **HLS 的缺点集中在"没做"，HFC 的缺点集中在"做错了架构"。** 前者可以增量补齐，后者只能推倒重来。

置信度【确定】。核心论据（4.2 的流式根因、2.5 的官方 hook 边界、2.4 的交互代价）均有源码行号支撑。

### 6.3 需要从 HFC 吸收的架构思想（而非代码）

即便不用 sidecar，HFC 有三点设计思想值得继承：

- **安装器事务化**：多文件 patch 必须纳入同一 manifest 事务，支持逐字恢复与块外改动检测。HLS 当前的单文件 `.bak` 不足以支撑生产。
- **兼容性证据化**：不只做字符串锚点匹配，还要输出「版本来源 / hook 策略 / 兼容性判定 / 建议动作」的可解释诊断。
- **fail-open 契约明确化**：任何插件侧失败都不得阻断 Hermes 主流程，且必须明确「已接管 / 未接管 / 结果未知」三态，避免消息重复或丢失。
